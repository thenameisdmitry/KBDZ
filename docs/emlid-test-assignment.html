Emlid test assignment: Base and rover setup

📄 Download the PDF version · Dmitrii Zhukov · October 2026

This page is my solution to the Emlid test assignment. It covers the Base and rover setup guide for Reach RS2/RS2+ in three parts:

  • Task 1. Audit: what works on the page, what doesn't, and why (professional opinion).
  • Task 2. Rewrite: the first part of the page rewritten by me, then I put a plan for the rest.
  • Task 3. Docs and AI: how an AI RAG agent changes my workflow.

Task 1. Audit​

The task

Read the page as the writer who owns it. Say what works, what doesn't, and why. Check that the guide gives the reader what they need for their task, no more and no less.

Reader: a first-time owner of two Reach RS2/RS2+ units, possibly new to RTK.

Reader's goal: get the rover to FIX over LoRa in one trip to the field, and understand what the coordinates are worth.

What works​

The page gets a lot right: a tight scope, a step-by-step flow that follows the real job, and all values in the text. View results is a fine wrap-up. The window check catches a radio problem before the field trip, which is critical.

Structure​

  • The two phases are invisible. The reader learns about the desk part and the field part only halfway down the page. That's a speed bump for a new reader, hence I'd name both phases up front.
  • No prerequisites. The tripod, pole, and Emlid Flow aren't listed before the steps.
  • The window check is buried in a tip. It should be the step that closes the desk part, with the antennas attached first and a clear "turn off and go" at the end.
  • Too many callouts. About a dozen on a short page, that is too much. I would leave two that matter (frequency rules, don't move the base) and make them a tip-sticker.

What to cut​

  • Defaults posing as required steps. GNSS and RTCM3 settings are already right on a new unit, but the steps don't say so. A guy with little experience does up to seven steps for nothing. I'd keep the steps, add one sentence that marks them as defaults, and collect all values in a reference table.
  • Lead-ins and wrap-ups. Sections open by restating the heading and close by announcing the next one. This wording stalls the reader: a quickstart should give the answer straight away.
  • Side notes in the wrong place. The sticker tip and the hotspot note belong in the steps. The RS+ note belongs in the prerequisites.

Language​

The text has a slight accent: a few non-native patterns slipped through (when + past simple, set at, define for identify, missing articles, etc.). It is also quite noticeable when it comes to the UI actions (tap, press, click, etc.)

What to add​

Must be confirmed with the product team: what Average SINGLE means for the results. Add explanation to the guide.

Proposed outline​

The page looks patched through UI changes without a structural review, and the RS3 guide is a near-copy. Every change multiplies across five translations, the PDF card, and the RS3 page, so I'd keep the sections and change as little as possible.

Questions for a device check (drafted with Claude)​

  • 1 Hz (base) and 5 Hz (rover): are both factory defaults? The RS3 guide uses 5 Hz for the base. Assumed yes, marked for verification.
  • Which LoRa settings are defaults? Assumed none, so they stay as explicit steps: a redundant step is cheaper than a failed link in the field.
  • Is it safe to transmit over LoRa without an antenna? Assumed no, so the antennas go on before the check.
  • What's the default averaging time? Assumed fine for a first setup.
  • Do the units keep their settings after power-off? Assumed yes. I found this on the Emlid community forum, but it needs confirmation.

Task 2. Rewrite​

The task

Rewrite one or two sections to show what "better" looks like. For the parts I don't rewrite, describe the changes and the reasons.

Scope. I rewrote the page from the top to the end of the desk part, plus the settings table that the base and rover sections point to. The rest of the page is described at the end. I kept the section names and their order. In Set up your base and Set up your rover, I kept the original steps and screenshots and changed only the framing and the language. Each section ends with a What changed and why block where you'll find my notes.

Rewritten page: Base and rover setup

Applies to: Reach RS2 and RS2+, set up in the Emlid Flow app.

Overview​

This guide shows how to do your first base-and-rover setup with two Reach RS2/RS2+ units. One unit is the base: it stays in one place on a tripod and sends correction data. The other unit is the rover: you carry it on a pole to measure points. With the corrections, the rover calculates its position with centimeter-level precision relative to the base. Emlid Flow shows this as the FIX status.

The base sends corrections over the built-in LoRa radio, so you do not need internet or cellular coverage. If you have internet access, see How to set up RTK over Emlid Corrections or Working with NTRIP service.

You work in two places:

  • At your desk: rename the units, set up the base and the rover, and check the connection.
  • In the field: place the units, set the base position, and wait for FIX.

Did you set up these units before? To check or restore the settings, go straight to Reference: settings for base and rover.

What changed and why
  • Merged the intro and Overview, which said the same thing twice.
  • Added a short explanation of base, rover, corrections, and FIX for first-time users. Experienced users can skip it, and the link to the reference table takes them straight to the values.
  • Added Applies to: the RS2 and RS3 pages are almost the same, so search readers and the AI agent need to see the product at once.
  • Named the two places where the reader will be working.

Before you start​

You need:

  • Two Reach RS2/RS2+ units with charged batteries
  • Two LoRa antennas
  • A phone or tablet with the Emlid Flow app
  • A tripod for the base and a survey pole for the rover

If you have not connected to a Reach unit before, see First setup.

note

All multi-band Reach receivers work together over LoRa. If you use a single-band Reach RS+ as the rover, the system works in single-band mode, because Reach RS+ tracks only L1 signals.

What changed and why
  • New section: the original lists the tripod and pole mid-guide and never mentions Emlid Flow. The RS+ note moved here from the top, because it is a special case.

Rename Reach devices​

All new Reach RS2/RS2+ units have the same name. Give each unit its own name, so you can easily tell the base from the rover.

  1. Connect to the unit that you want to use as the base.

    Which unit am I connected to?

    When you connect, all LEDs on the unit blink at the same time. To blink them again later, tap the receiver name on the Receivers screen, then tap Flash LEDs.

  2. Go to Settings and tap Receiver info.

  3. In Receiver and hotspot name, enter reach-base. This name is also the name of the unit's Wi-Fi network in hotspot mode.

  4. Tap Save.

  5. Put a sticker from the package on the unit, so you can see which unit is the base.

  6. Do steps 1–5 for the second unit. Use the name reach-rover.

Result: When you connect to a unit, Emlid Flow shows its new name.

What changed and why
  • The expandable block now asks the reader's question. The hotspot note and the sticker tip are now steps, because they are actions.
  • Added a result. All buttons use one verb: tap.

Set up your base​

Steps 2–6 set values that a new unit already has. Check them and change only what is different. All values are also in Reference: settings for base and rover.

  1. Connect to reach-base.

  2. Go to Settings and tap GNSS settings. Select all satellite systems.

  3. Set the GNSS update rate to 1 Hz and apply the changes.

  4. Go back to the Receivers screen and tap Base settings. Then go to RTCM3 messages.

  5. Set the RTCM3 messages (the correction data that the base sends) as follows:

    • ARP station coordinates: 0.1 Hz
    • Other MSM4 messages: 0.5 Hz

  6. Tap Apply.

  7. Go back to the Receivers screen and tap Base output. Select LoRa.

  8. Tap Edit in the LoRa cell. Select a frequency and set the output power to 20 dBm.

    caution

    Select the frequency and output power that your local regulations allow. If your region has restrictions, the frequency band is limited automatically.

  9. Set the air data rate to 9.11 kb/s and tap Save. Note the frequency: the rover must use the same frequency and air data rate.

Result: The base is set up to send corrections over LoRa.

What changed and why
  • Kept the original steps and screenshots: they are clear, and this is the only place where these settings are shown.
  • Added one sentence before the steps: steps 2–6 are defaults on a new unit. A newcomer knows to only check them. A user who changed them knows these are the values to restore.
  • Steps 4 and 7 now say which button to tap, and step 3 asks to apply the changes, as the rover section already does. RTCM3 messages gets a short explanation for newcomers.

Set up your rover​

Steps 2–3 set values that a new unit already has. Check them and change only what is different. All values are also in Reference: settings for base and rover.

  1. Connect to reach-rover.

  2. Go to Settings and tap GNSS settings.

  3. Select all satellite systems and set the GNSS update rate to 5 Hz. Apply the changes.

  4. Go back to the Receivers screen and tap Correction input.

  5. Select LoRa. Set the same frequency as on the base and the air data rate to 9.11 kb/s. Tap Save.

Result: The rover is set up to receive corrections from the base over LoRa.

What changed and why
  • Same approach as the base: the original steps and screenshots + one sentence about defaults.
  • Step 3 names the values instead of "the same GNSS systems as for the base". The section now works on its own, for a reader who jumps here and for the AI agent.

Check the connection​

Check the link at your desk, before you go to the field. It is easier to fix a problem here.

  1. Attach the LoRa antennas to both units.
  2. Put both units near a window, so they can see the sky. Wait a few minutes.
  3. In Emlid Flow, connect to reach-rover and open the Status screen.
  4. Scroll down to the Corrections section.

Result: The Corrections section shows that the rover receives corrections from the base.

If the rover does not receive corrections, check that both units use the same frequency and air data rate, and that both antennas are attached.

When the connection works, turn off both units and take them to the field. The units keep their settings.

What changed and why
  • The "check by the window" tip is now a required step, with the antennas attached first.
  • Added a result, a short fix, and a clear end to the desk part. The original asks the user to turn the units on in the field, but never to turn them off.

  • New section for the readers' reference. These values are not documented anywhere else. The table gives them a permanent place, a stable anchor for support, and a clear source for the AI agent. The Default column shows what to check and what to change.

The rest of the page (described, not rewritten)​

Place Reach RS2/RS2+ units > Set up in the field. Keep the steps, but remove "attach the antennas" (now done at the desk). Make the "open sky part" the first step, not a note. Keep "do not move the base while it averages" as the only caution. Add two sentences on what Average SINGLE means for the results, and a recommended averaging time (both to be confirmed with the product team).

The section ends with the result of the base setup. I'd keep this text and its screenshot, with a light language edit:

When the base finishes averaging, the Base marker section shows its coordinates. The base is now set up and sends corrections to the rover.

View results. Keep the status descriptions, because they are the strongest part of the page. Add If the rover does not get FIX with two or three likely causes. It is critical to add a link to the Troubleshooting section.

Language. Use the same rules as above: one verb per action, set to, articles before base and rover, and the names base and rover instead of four different names.

Task 3. Docs and AI​

The task

The documentation is also a source for an AI customer agent. Does this change how I would write or structure a procedural guide like this one?

Short answer: yes, but not much. The problem is that a RAG AI agent reads chunks of the doc, not pages. It has no navigation, no visual hierarchy, no neighboring sections. Whatever a human infers from context, the agent either loses or invents. So the job is to make the implicit explicit.

How I'd write​

  • Self-contained sections. Avoid references like "same as for the base." Each section names the device, its role, and the screen: this way, the AI will find the references itself and digest them into a proper response.
  • The product in the text, not only in the URL. The RS2 and RS3 guides are near-identical but use different values. Need to put the product in headings and body text, add metadata as well.
  • Facts as structured data. A settings table gives a precise answer to "what should my base output?" and one canonical home for default values.
  • Conditions and importance in words. To the agent, a caution box is just another paragraph (as stated above). The wording must emphasize the importance of the information given in the guide.

How I'd work​

  • RAG testing as a docs-as-code stage. Each page gets a small set of real customer questions with expected answers. On every docs PR, CI runs them through the agent, and an LLM judge flags regressions: wrong facts or the wrong product. AI also proposes new questions from page diffs and agent logs. A writer reviews failures and owns the set.
  • Agent errors as backlog. A wrong answer usually points to a gap, an ambiguity, or a conflicting duplicate, including a stale translation. Problems like these go straight to the backlog with high priority.

What I wouldn't do is rewrite procedures for the bot: no FAQ-style pages and no keyword stuffing. That's an old solution, which doesn't work any longer.
