Case 1: Algorithmic Reconciliation Guide

Format

Knowledge base article examining the Algorithmic Reconciliation process at the core of the Reconciliation Manager module.

Target Readers

Quantitative analysts, financial data engineers, portfolio risk managers, and fund accountants.

Description

Original internal research and analysis of a company-developed self-learning engine algorithm, demonstrating how it reconciles Security entities across multiple data sources using Fuzzy logic.

Business Impact

Used by hedge funds and banking accounting systems for daily reference data accuracy. Critical for collateral management, loan positions, cashflows, and projected portfolios. Contributed to a 70% increase in module sales.

Introduction​

Reconciliation Manager is an administrative dashboard that helps confirm portfolio elements against counterparties and accounting systems. It enables clients to manage portfolio figures and ensure accurate reconciliation to mitigate operational risks and errors.

Reconciliation Manager offers two data reconciliation solutions: Classic and Algorithmic. This Guide provides user instructions and explains the working principles of Algorithmic Recon.

TermAlgorithmic Recon

A data reconciliation engine based on Fuzzy logic. The Algorithmic Recon engine is a machine-learning background process that uses a special algorithm to calculate certainty and identify the best entity match based on reconciliation history.

TermFuzzy logic

A form of probability theory that calculates "degrees of truth" rather than the usual "true or false" Boolean logic. It addresses partial truth, where the truth value may range between completely true and completely false. Fuzzy logic is used in many fields, such as artificial intelligence. In the Algorithmic Recon, it powers the machine-learning process at the core of the engine.

Security Recon runs in two phases: ID-Based Recon and Algorithmic Recon. ID-Based Recon runs first and processes only Listed Securities and Equity Swaps. Algorithmic Recon runs second and covers all Securities, including those not matched during the first phase. This document describes the second phase: Algorithmic Recon.

  • Security Analysis: retains Securities with Strong, Weak, Potential, and Ambiguous map types assigned as a result of Security Algorithmic Recon.
  • Not Mapped Securities: contains Securities not included in any Positions’ search spaces for the Algorithmic reconciliation process.
  • Reinforcement Learning: contains and analyzes Algorithmic Recon data in a matrix table.
  • Rejected Mappings: contains Security mappings from the Weak certainty group that users rejected on the Security Analysis screen.
INFORMATION

The Security Mappings screen in the ID-Based Security Recon toolbox is also considered part of Algorithmic Recon because it aggregates all extracted Securities mapped to system Securities (using both ID-Based and Algorithmic methods).

Security Algorithmic Recon: Principle of Work​

Security Algorithmic Recon, built on Fuzzy logic, follows a working principle different from Classic Security Recon. Security entities are extracted from the HUB_POSN and HUB_MRGD files (which contain Position records). The matching algorithm consists of the following steps:

Step 1: Search space formation​

The search space is formed for Positions on the left side (House-side entities) and on the right side (Counterparty feed files).

When Positions are extracted from the HUB_POSN and HUB_MRGD feed files, a search space is created for each right-side Position (Counterparty feed file). The search space is a pool of possible matches selected by the parameters Account, Direction, and Settlement Date. A Cartesian join method is used for this step. Positions A, B, and C are candidates for collation on the House side because their basic parameters match. This forms the search space for Fuzzy logic reconciliation. The Algorithmic Recon Fuzzy engine then determines which candidate is the correct match.

Positions with expired Securities (past their Maturity or Expiry date) do not participate in reconciliation and are excluded from the search space in the first step of the algorithm.

INFORMATION

It is common for a House Position to be split into several Positions for business or planning purposes (for example, by Position strategy). In that case, multiple House Positions may be matched to a single Counterparty Position (for example, in bank reports). The matching routine proceeds in the same way as regular one-to-one matching.

Step 2: Pair Similarity calculation​

Pair Similarity calculation is performed for Positions within the search space, using three Predicates for a specific group of fields and the selected Strategy.

To determine the correct candidate, the Algorithmic Recon engine calculates the Pair Similarity value. This value is assembled from three Predicates computed for each candidate.

TermPredicate

A calculated variable that represents the matching strength of Position and Security entities and is used to compute the Pair Similarity value. Predicates are based on the matching fields of reconciled right-side and left-side Position items. Algorithmic Recon uses three Predicates: Position required fields (Quantity and Market Value Local), Security description fields (ISIN, Cusip, Underlying Security, Issuer, Description, etc.), and Position additional fields (Market Value Book, Price Local, FX Rate, Daily Accrual Basis, etc.).

Position required fields have the highest weight at 0.4, Security description fields have a weight of 0.35, and Position additional fields have the lowest weight at 0.25. Together, the three Predicates sum to a total weight of 1.

Therefore, the algorithm scans the fields of the Counterparty Position and House Position candidates, starting with the most important fields: Quantity and Market Value Local, which form the first Predicate target group (Position required fields).

Values may be missing on one side of the comparison. For example, the House Position may have the ISIN field populated while the Counterparty file does not (or vice versa). In these cases, the Fuzzy engine applies the Recon Missing Values Strategy.

TermRecon Missing Values Strategy

A two-way method used during field collation when compared Positions lack a value on one side but have it on the other. When the Recon Strategy is set to Optimistic, the system assumes the missing value matches the value on the opposite side, which adds points to the computed Predicate. When the Recon Strategy is set to Pessimistic, the system assumes the missing value does not match the value on the opposite side, which subtracts points from the Predicate.

INFORMATION

When both sides lack data in the compared field, the Recon Strategy is not applied and does not affect the Predicate result.

CRITICAL FAILURE IN FIELDS COMPARISON

The second Predicate, Security description fields, includes fields that compare the Securities attributes of Positions on opposite sides. These fields are grouped into two sets: Required and Sufficient.

  • Required is a group of highly critical values (Security Type, Currency Code, Effective Date, Strike Price, Underlying SEDOL, Underlying CUSIP, Underlying ISIN). If values in these fields do not match, the Predicate’s weight decreases sharply, which reduces the chance of a match. If they do match, the weight increases slightly.
  • Sufficient is a group of values with lower criticality (SEDOL, CUSIP, ISIN, Ticket, RIC, and Security Code). These fields may legitimately differ for the same Security. For Sufficient fields, a match drives a sharp increase in weight, while a discrepancy causes a sharp decrease.

When all three Predicates are calculated, the Pair Similarity value is assembled for each candidate. Pair Similarity ranges from zero to one hundred, where zero indicates a complete mismatch across all Position and Security fields and one hundred indicates a perfect match across all fields.

In general, each mismatch subtracts points from the Predicate. It is unlikely that all Predicates will achieve the full combined weight of 1. As a result, Pair Similarity works like a competition: the highest-scoring candidate is selected to match with the House Security.

Based on the search space formed using the Position parameters (Account, Direction, and Settlement Date), there are four candidates for the right-side Security with the appropriate Security Map Type. Pair Similarity is then calculated for each candidate:

  1. GLTUK2022: has only one matching Security Description field. Pair Similarity is computed as 13% probability.
  2. GLTUK-RA: has three matching fields, one of which adds points to the Position required fields Predicate. In addition, the critical values in the second Security description field Predicate match. Pair Similarity is computed at 76% probability.
  3. GL-T-UK22: also has three matching fields, but none align with the highest-weighted Predicate. Pair Similarity is computed at 59% probability.
  4. GTU: this candidate has the lowest Pair Similarity at 0 percent probability, since no fields match on the right side.

In this reconciliation round, GLTUK-RA scores the highest Pair Similarity and is therefore mapped to the right-side Security. However, whether the mapping is automatically approved, requires user approval, or is classified as a potential map is determined in the third step of the reconciliation process.

Step 3: Best Pair selection​

Based on the calculated Pair Similarity value, the system selects the best Securities for mapping.

Position matching based on the highest Pair Similarity leads to a key step in Security Recon: matching Securities within Positions. Securities inherit the Pair Similarity score of their Positions. This Security Pair Similarity determines the mapping strength applied in phase four.

The Pair Similarity for Positions (and for Position Securities) is calculated using the engine logic described in Step 2.

Step 4: Mapping Strength​

The system determines the mapping strength for the best Pair Similarity scorer, based on the Confidence Level and Distance.

After the engine identifies the winner of the matching contest, it determines the mapping strength. There are four possible mapping strengths:

  • Strong: high accuracy, mapping is created automatically.
  • Weak: decent accuracy, mapping is created but requires the user’s approval.
  • Potential: low accuracy, mapping is automatically added to the Candidates list and can be reviewed; mappings can then be created manually.
  • Ambiguous: undecided mapping, since the Pair Similarity of matching candidates is identical; in this case, the mapping conflict must be resolved manually by a user.

The engine determines the mapping strength based on two parameters (Confidence Level and Distance) and their ratio within the Reinforcement Learning matrix.

TermConfidence Level

Mapping certainty value. This value is taken directly from the calculated Pair Similarity of the reconciliation winner. The higher the Confidence Level, the stronger the mapping.

TermDistance

Difference between the Pair Similarities of the reconciliation winner and the second-place candidate. The greater the difference between the winner and the closest competitor, the higher the certainty of the mapping.

If there is only one candidate in the search space, the Distance equals the Confidence Level.

Confidence Level and Distance form the axes of the Reinforcement Learning matrix table. The matrix table is available on the [Reinforcement Learning screen] (#reinforcement-screen).

TermReinforcement Learning matrix table

Dynamic, self-modifying table. Columns represent Confidence Level diapason chanks, and rows represent Distance diapason chanks. These diapason chanks are calculated based on the overall set of Algorithmic mappings: the more mappings are created with different Confidence Levels and Distances, the shorter the diapason chanks become.

IMPORTANT

The position of a new mapping on the matrix table determines its strength: landing in a green cell defines a Strong mapping, landing in a yellow cell defines a Weak mapping, and landing in a white cell grants a Potential status.

Ambiguous mappings are not considered in the matrix table unless the mapping conflict is resolved manually by a user.

SELF-LEARNING MECHANISM OF THE ALGORITHMIC RECON ENGINE

In an ideal situation, with equal proportions of reconciled data and no discrepancies or user corrections, the ratio of the Strong/Weak/Potential zones in the Reinforcement Learning matrix table would be approximately as follows:

Indeed, the smaller the difference in Pair Similarity between a low-Confidence Level winner and the second-place candidate, the higher the odds of an erroneous mapping. By contrast, the higher the Confidence Level and the larger the gap between Pair Similarities, the smaller the margin for error.

In practice, mismappings occur across different Confidence Levels and Distances, so the strength ratio within the Reinforcement Learning matrix is constantly changing. For example, when a user finds an error in a Strong mapping and corrects it, the green Strong cell where the mapping landed is downgraded to Weak or Potential.

As a result, the final decision on mapping strength depends on a self-learning mechanism that adapts dynamically to mapping history and user corrections. The more entities are mapped, the more mappings are confirmed, and the more errors are corrected manually, the smarter the Fuzzy engine becomes.

The Reinforcement Learning screen allows users to dive deep into mapping statistics, review mapping Pair Similarities and Predicates at different levels, and analyze mappings alongside the Fuzzy engine.

Step 5: Reconciliation results​

System populates Security Mappings, Security Analysis, and Not Mapped Securities screens: for reconciled Security entities, these screens are populated with Algorithmic Recon results.

In the Algorithmic Recon final phase, the system populates the screen grids with reconciliation results. There are three resultant screens of Security Algorithmic Recon:

  • Security Mappings: an aggregation screen that shows all mappings and mapping suggestions in the system for a designated period.
  • Security Analysis: an operational analysis screen that contains mapped and not-mapped Securities, and allows users to create, approve, reject, and break mappings.
  • Not Mapped Securities: an aggregation screen that contains only not-mapped Securities, allowing users to review and manually map entities that have no mappings.

Once the results are allocated in the system, users can begin reviewing Securities mappings, approving Weak mappings, creating Potential mappings, and correcting errors.

Reinforcement Learning​

Reinforcement Learning is an operational analytics screen that consolidates and analyzes Algorithmic Recon data in a specialized matrix table.

It recalculates the accuracy of previously created mappings and generates a heatmap of accuracy zones for Algorithmic Recon mappings. For details, refer to the Principle of Work section.

  1. Date selector: selects the time range for Reinforcement Learning statistics.
  2. Distance rows: Distance parameter diapason chunks.
  3. Quality parameters: sub-rows showing quality parameters (Total verified, Verified as correct, Unverified).
  4. Confidence Level columns: Confidence Level diapason chunks.
  5. Totals: totals per Quality Parameter group for each Distance row.
  6. Summary: averages for Strong, Weak, and Unused mappings, including Accuracy and Coverage for each group.
INFORMATION

The Reinforcement Learning screen is scheduled to run once per day at the end of the day for the previous business day. During the run, Reinforcement Learning recalculates Confidence Levels and Distances for all mappings (including approved and rejected mappings), gathers statistics, and regenerates the accuracy zones in the matrix table. To do this, Algorithmic Recon runs for the past date using real historical input and produces new outputs for mappings and mapping suggestions. These outputs are then compared with existing real mappings (Etalon mappings): verified, approved, rejected, corrected, or manually created.

FUZZY ENGINE SELF-LEARNING PROCESS

By comparing the calculated outputs of an Algorithmic Recon run with Etalon mappings, the Fuzzy engine can self-learn and evolve. This learning process enables the engine to calculate actual accuracy for each Confidence Level/Distance segment and apply a similar expected accuracy rate to future mappings within the same segment. Segments are divided into three groups:

  • Strong (matrix green cells): accuracy is higher than 99,5%.
  • Weak (matrix yellow cells): accuracy is between 98% and 99,5% (that is, at most one error per hundred mappings).
  • Potential (matrix white cells): accuracy is less than 98%.

As a result, the Reinforcement Learning matrix table dynamically adjusts the heatmap accuracy zones based on automatic Strong mappings, approvals and rejections of Weak mappings, and manual mappings created by users.

NOTE

Due to the dynamic nature of the Reinforcement Learning matrix table, the number of columns and rows (and the chunk ranges) change automatically and are not controlled by the user. The matrix table skeleton is calculated based on the average distribution of mapping volume (each row and column includes the nearest number of mappings).

Important

The Reinforcement Learning matrix begins to work only after the system accumulates a significant number of verified matching instances. This threshold is set individually for each client during implementation (the default value is 10,000 matching instances).

Additionally, the accuracy zones shift in response to users breaking mappings. For example, the Strong cell for a Confidence Level of 89–93 with a Distance of 1–30 can be downgraded to Weak or Potential if a user manually breaks a Strong mapping they deem incorrect within this cell.

Matrix table​

Matrix table shows the accuracy zones of Strong, Weak, and Potential Map Types for Security mappings. Rows represent Distance ranges, and columns represent Confidence Level ranges. Each cell contains three quality parameters:

  • Total verified: number of legitimate mappings (constituted from correct and rejected mappings).
  • Verified as correct: number of mappings that were verified (constituted from approved mappings, manually created mappings, or mappings created by Classic Recon).
  • Unverified: number of mappings that are not currently verified (constituted from mappings that require approval and have not yet been approved).

Each value lets users drill down to the list of mappings within that Distance and Confidence Level segment. When a value is clicked, the user is directed to the Learning Details grid.

Summary​

Summary is an overview at the bottom of the Reinforcement Learning matrix table. It shows the totals for Total verified, Verified as correct, and Unverified mappings across all three groups (Strong, Weak, and Unused). It also displays each group’s Accuracy and Coverage:

  • Accuracy: calculated as the total number of suggested mappings verified as correct divided by the total number of suggested verified mappings.
  • Coverage: calculated as the total number of suggested Broker Security-to-House Security mappings divided by the total number of not mapped Broker Securities.

Learning Details​

Learning Details is an overlay screen that displays all mappings within the selected matrix-table cell and quality parameter. To open the Learning Details grid, click a value in the matrix table on the Reinforcement Learning screen:

  1. Model Id: currently not used filter.
  2. Confidence From/To: specify the Confidence Level range to filter Securities in the grid. Default values are taken from the selected cell on the matrix table.
  3. Distance From/To: specify the Distance range to filter Securities in the grid. Default values are taken from the cell of selected value on the matrix table.
  4. Grid: Security mappings displayed based on the selected filters.
  5. Context menu: selective options that can be performed against the Security mapping.

Not Mapped Securities & Rejected Mappings​

The Not Mapped Securities and Rejected Mappings screens are aggregation grids for, respectively, Securities that did not find a match and Security mappings that were rejected by users.

Not Mapped Securities​

The Not Mapped Securities grid contains Securities extracted from incoming feed files that were not included in any Positions’ search spaces for the Algorithmic reconciliation process. As a result, reconciliation was not performed because there were zero mapping candidates.

  1. Date To: select the date for which to display not mapped Securities.
  2. Reprocess: press the button to open the Algorithmic Recon Reprocess screen and initiate the reprocess procedure.
  3. Grid: list of not mapped Securities for the selected day.
  4. Context menu: contains the Details option that opens the Mapping Details pop-up screen.

Rejected Mappings​

The Rejected Mappings grid contains Security mappings from the Weak certainty group that users rejected on the Security Analysis screen.

  1. Grid: list of mappings in the Rejected state.
  2. Context menu: contains the Restore Mapping option, which returns the mapping to its previous state.
Important

Rejected mappings directly impact the Algorithmic reconciliation processes. Before starting, the Fuzzy algorithm checks the pool of rejected mappings; if it finds a mapping flagged as Rejected, it excludes entities with the same Security Code, Map Type, and Company ID from the search space.
