# How I Work

The samples in this portfolio come from a documentation system I designed and ran for eight years. This page explains that system. Good docs are not a writing effort, they're an operating process.

## Principles

**Docs start where users get stuck.** I came to technical writing from five years in support and implementation. Every guide I write starts from a real failure point: a recurring ticket, a stalled onboarding, a misused feature, not from the system architecture.

**Documentation is a product.** It has users, a roadmap, a backlog, releases, and success metrics. I ran it that way: prioritized by user impact, shipped on schedule, measured by outcomes.

**If it's done twice, automate it.** Repetitive documentation work is a bug in the process.

## Information architecture

The knowledge base I built at Hazeltree grew to **200+ guides across 18 product modules**, and stayed navigable because the architecture was decided before the content:

- **One structure for all modules.** Every module followed the same pattern (overview, setup, workflows, reference, troubleshooting) so users who learned one module could navigate any other.
- **Single source of truth.** Shared concepts (glossary terms, common procedures, screenshots of shared UI) lived in one place and were reused, not copied. This pushed content reusability to **~80%** and made global updates a one-file change.
- **Layered depth.** Each guide works at three reading depths: skim the headings, read the workflow, or descend into the reference tables, so the same document serves a new user and an expert.

## Docs-as-code pipeline

Documentation lived in version control and moved like code:

1. **Author** in Markdown, in a branch.
2. **Review** is peer review for language and standards, SME review for technical accuracy, both as pull-request reviews with tracked comments.
3. **Merge and publish** through the same pipeline every time, no manual uploads, no "final_v2" files.

This gave the team full history, painless rollbacks, parallel work on the same doc set, and a review trail for every change.

## Release workflow

Documentation shipped in lockstep with the product: **60+ releases** over my tenure:

- Doc work was scoped during feature planning, not after code freeze. I sat in planning sessions with Product and Engineering, which also let me flag UX and naming issues before they shipped.
- Each release produced: updated guides, API reference updates, and release notes cross-linked to the relevant documentation (see the [Release Notes sample](/docs/portfolio/releasenotes)).
- **Release notes were generated by a Python pipeline I built**, drawing on structured inputs from the tracker and AI-assisted drafting (Claude, Copilot) with human review. This roughly **doubled delivery efficiency** - the writers' time went to guides, not changelogs.

## Quality loop

- **Support tickets were the feedback channel.** Recurring questions became documentation tasks; documentation fixes were tracked against ticket volume. Over time, self-service documentation cut support workload by **~30%**.
- **Standards were written down.** A living style guide covered terminology, screenshot conventions, and structure templates, which is what made review fast and the KB consistent across writers.
